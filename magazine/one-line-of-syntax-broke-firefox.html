One line of syntax, and Firefox could never play the game

23 August 2026 Team Bonding 6 min read

Players said Team Bonding did not work in Firefox. It did not — in any version of Firefox that has ever shipped, and in Safari before 18.4. The cause was eleven characters, and the reason nobody caught it is that in Chrome those eleven characters are correct.

The report was as thin as reports get: some players said the game did not work in Firefox. No error, no version, no step that failed.

It was completely correct, and worse than it sounded. Not marginally broken, not broken on an old build — broken in every version of Firefox that has ever been released, including the current one, and broken in Safari older than 18.4. Here is the line.

this.renderer.domElement.requestPointerLock?.().catch(() => {});

Pointer Lock has two different contracts

Pointer Lock is how a first-person game takes the mouse: the cursor disappears, and raw movement drives the camera instead of a pointer. Asking for it is one call, and that call means two different things depending on who implemented it.

The shipped W3C specification says requestPointerLock() returns nothing. It reports the outcome later, by firing pointerlockchange or pointerlockerror on the document. A proposed change to that specification says it returns a Promise instead. Both behaviours are live in browsers right now.

browser    requestPointerLock    returns a Promise?
Chrome     37                    yes, from 92
Safari     10.1                  yes, from 18.4  (March 2025)
Firefox    50                    no  -  no version, current release included

So on Firefox and on Safari 18.3 and older, .catch(...) reads a property of undefined and throws a TypeError, synchronously, right there.

The optional call does not save you

The ?.() in that line looks like it is guarding exactly this. It is not, and the distinction is worth having in your head, because it is easy to write in good faith.

?.() asks whether the thing you are calling exists. On Firefox, requestPointerLock exists — it has existed since Firefox 50. It is a perfectly good method that does its job. It simply does not hand back something with a .catch on it. The guard checked the wrong half of the expression: it protected the call and left the result unprotected.

Optional chaining protects you from a method that is missing. It does nothing about a method that returns something other than what you assumed.

Why Chrome never told us

Chrome started returning a Promise in version 92, released in 2021. Every browser used to build this game returns a Promise. The line is correct in the only environment it was ever run in, which is the most durable way for a defect to survive.

Why it presented as "it does not work"

The failure shape is the reason a real problem sat in production disguised as a vague complaint.

It is not a crash. The page loads, the menu draws, the maps are there, the character picker works. Nobody pastes a stack trace, because from the outside there is no stack trace — there is a click that does nothing. It is not a load failure either, so nobody says "it will not load". What a player experiences is that they press Play and the mouse does not capture, and the sentence that produces is "it does not work on Firefox", which is unactionable and was quite right.

The fix, and what it is not

A small compatibility shim now makes requestPointerLock return a Promise in every browser, by wrapping the native method and resolving it from the pointerlockchange and pointerlockerror events where the native call does not resolve itself. The game calls one function and gets one contract.

It is covered by tests that run the exact production expression against a fake browser implementing each of the two contracts — the expression, not a paraphrase of it, because a paraphrase is a test of the paraphrase.

The limit of all of the above. Firefox and Safari were never run. The only browser available on this machine is Chromium. The fix is proven against a faithful fake of each contract and against the published browser compatibility data, and that is a genuinely weaker claim than having opened Firefox and played a round.

If you play Team Bonding in Firefox or in Safari and the mouse still does not capture, that is worth telling us. It would be the only evidence that exists.

The general shape

The supported floor for the game is now Chrome and Edge 89, Firefox 108, Safari 16.4 — set by the newest platform feature the game page needs, not by anything in the game.

The transferable part is smaller than a browser bug. Any API whose return value differs between implementations will be silently correct in whichever one you develop in, and a null-safety operator applied to the wrong half of the expression will look like diligence in review. The only thing that catches it is running the actual line against the other contract.
